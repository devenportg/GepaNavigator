# 1.3 Функционал и архитектура системы

## 3.1 Функциональная декомпозиция

Система ГепаНавигатор состоит из 8 функциональных блоков.

---

### Блок 1. Автоматический регистр пациентов с гепатитами

**Назначение:** автоматическое формирование и поддержка регистра пациентов, подлежащих диспансерному наблюдению.

**Триггеры постановки на учёт:**
- Появление диагноза по МКБ-10 группы B18.* (хронические вирусные гепатиты) в ГИС ЭЗ РТ.
- Положительный результат ПЦР на РНК ВГС / ДНК ВГВ / РНК ВГД.
- Положительный серологический маркер (HBsAg, anti-HCV) при наличии клинических показаний.
- Появление записи о пациенте в Федеральном регистре больных вирусными гепатитами (ФРВГ).
- Импорт из внешних систем и ручной ввод документов.

**События снятия с учёта:**
- Снятие по КР (достижение УВО + истечение срока посттерапевтического наблюдения).
- Смерть пациента.
- Переезд в другой регион / снятие с прикрепления.
- Ошибочная постановка (отмена диагноза).

**Функции:**
- Автоматическое создание/обновление записи в регистре при поступлении триггера.
- Разрешение дубликатов по ФИО+ДР+СНИЛС+ОМС.
- Ведение статуса наблюдения: Активный / На терапии / Посттерапевтический контроль / Снят / Умер.
- История изменений статуса (аудит).

---

### Блок 2. Клинический маршрут по КР (Decision Support / клинический слой)

**Назначение:** автоматический расчёт индивидуального плана наблюдения для каждого пациента на основе клинических рекомендаций и приказа № 168н.

**Учитываемые параметры:**
- Нозология (ВГВ / ВГС / ВГД / микст).
- Стадия фиброза (F0–F4).
- Цирроз (да/нет) → отдельная ветка: скрининг ГЦР каждые 6 мес (УЗИ + АФП).
- Проводится ли в данный момент ПВТ → фаза контроля на терапии.
- Посттерапевтическая фаза → контроль УВО-12, УВО-24.
- Коинфекции (ВИЧ, ВГД), коморбидность.

**Функции:**
- Генерация индивидуального плана наблюдения с конкретными датами.
- Расчёт окна допустимости каждого обследования (с гибкостью, например визит допустим в диапазоне ±14 дней).
- Автоматический чек-лист на текущий приём: какие анализы/обследования должны быть выполнены.
- Контроль УВО-12 (12 недель после окончания ПВТ) — отдельный критический триггер.
- Выявление просроченных событий и формирование списка «выпавших» пациентов.
- Учёт противопоказаний и индивидуальных отклонений по решению врача.

---

### Блок 3. Рабочее место врача (одно окно)

**Назначение:** единый экран врача-инфекциониста, заменяющий 4 системы + Excel.

**Подблоки:**
1. **Список пациентов на текущий день/неделю/месяц** с цветовой разметкой:
   - зелёный — все запланированные обследования выполнены;
   - жёлтый — есть запланированные, но не просроченные;
   - красный — есть просроченные события;
   - фиолетовый — через 4–6 недель контроль УВО.
2. **Карточка пациента:**
   - паспортная часть;
   - сводка анамнеза и текущего статуса;
   - вирусологическая характеристика (генотип, нагрузка);
   - история ПВТ и ответов на терапию;
   - динамика ключевых показателей (АЛТ, АСТ, вирусная нагрузка, фиброз);
   - чек-лист предстоящих обследований.
3. **План приёма** (автогенерация по КР с возможностью корректировки врачом).
4. **Черновик заключения приёма** с помощью YandexGPT на основании выбранных данных карты и текстовых заметок врача; результат всегда проверяет и редактирует врач.
5. **История взаимодействий и предыдущих заключений.**


---

### Блок 4. Управление приёмом и эскалация (Care Management)

**Назначение:** предотвращение выпадения пациента из наблюдения.

**Функции:**
- Планирование даты следующего визита при закрытии текущего.
- Формирование задания для среднего медперсонала обзвонить пациентов из «красной зоны».
- Журнал исходов обзвона (пациент придёт / отказался / не отвечает / недоступен).
- Маршрут эскалации: пациент не пришёл → напоминание → обзвон → уведомление заведующему → отметка в отчёте.

---

### Блок 5. Коммуникация с пациентом

**Назначение:** проактивное информирование пациента и поддержка приверженности.

**Каналы:**
- СМС-уведомления.
- Push/уведомления в региональный портал пациента.
- Уведомления через Госуслуги (интеграция с ЕПГУ).
- Голосовой робот обзвона (опционально).

**Типы сообщений:**
- Напоминание о предстоящем визите (за 7 и за 1 день).
- Напоминание сдать анализы до визита (за 10 дней).
- Напоминание о контроле УВО-12 после терапии.
- Информация о готовности результатов.
- Образовательные материалы о гепатите и терапии.

**Настройки:**
- Согласие на информирование (юридическое основание по 152-ФЗ).
- Частота и предпочитаемый канал.
- Отписка.

---

### Блок 6. Интеграции

| Интеграция | Назначение | Протокол/формат |
|---|---|---|
| ГИС ЭЗ РТ (основная МИС) | Чтение диагнозов, визитов, назначений; запись заключений; запись в расписание | Нативное встраивание (iframe/SDK)/REST |
| ЕГИСЗ | Передача структурированных данных ДН, сведения о прикреплении | РЭМД/СЭМД, НСИ, web-сервисы ЕГИСЗ |
| ФРВГ (федеральный регистр вирусных гепатитов) | Получение сведений о пациентах, отправка отчётности | Регламентированный обмен Минздрава |
| Лабораторные ИС (ЛИС) | Получение результатов ПЦР, ОАК, БАК, АФП | HL7 FHIR / HL7 v2 / нативные адаптеры |
| Центры эластометрии / УЗИ | Получение результатов инструментальных исследований | FHIR DiagnosticReport / адаптеры |
| ЕПГУ (Госуслуги) | Отправка уведомлений пациенту, запись на приём | СМЭВ / API Госуслуг |
| Внешние справочники | МКБ-10, РЛС, справочник медорганизаций | НСИ ЕГИСЗ |
| YandexGPT | Текстовый черновик заключения по явно выбранному контексту; финальное решение и редактура — за врачом | Опциональный Yandex Cloud AI Studio Chat Completions API; выключен по умолчанию и предназначен только для синтетических данных |

---

### Блок 7. Аналитика и дашборды

**Назначение:** операционная и управленческая отчётность.

**Уровни:**
1. **Врач:** нагрузка на месяц, доля явившихся, пациенты в красной зоне.
2. **Заведующий отделением / главврач МО:** показатели по своей МО в сравнении с планом и среднерегиональным.
3. **Минздрав РТ:** региональный дашборд.
4. **Федеральный уровень:** агрегированные показатели для НМИЦ ФПИ.

**Ключевые метрики:**
- Охват диспансерным наблюдением (доля пациентов с B18.* в регистре из всех выявленных).
- Приверженность (доля явившихся на плановый приём в окне допустимости).
- Доля пациентов, обследованных согласно КР (по видам обследований).
- Доля достигших УВО-12 / УВО-24.
- Частота пропущенных визитов и цикл закрытия просрочки.
- Нагрузка на одного инфекциониста (пациенты/визиты в месяц).
- Вклад региона в цель элиминации гепатита C.

**Реализация:** встроенные в приложение отчёты на PostgreSQL; отдельный BI-сервис не используем.

---

### Блок 8. Администрирование, безопасность и аудит

**Функции:**
- Управление пользователями и ролями (инфекционист, зав. отделением, главврач, оператор МИАЦ, аналитик Минздрава, администратор).
- Разграничение доступа по МО и уровню агрегации (врач видит только своих пациентов; главврач — свою МО; Минздрав — весь регион).
- Журнал всех действий с медицинскими данными (who/when/what).
- Политика паролей, СЗИ от НСД, соответствие требованиям ФСТЭК (приказ №21, ПП-1119).
- Шифрование данных в покое и в канале (TLS).
- Для демонстрационного YandexGPT передаётся только минимально необходимый контекст; системные ФИО и идентификаторы исключаются, запрос выполняется только по действию врача. Нельзя передавать реальные персональные или медицинские данные. Любое клиническое применение требует отдельной проверки требований к данным, безопасности и договорных условий.
- Мониторинг доступности и инцидентов ИБ.

## 3.2 Нефункциональные требования

| Атрибут | Требование |
|---|---|
| **Доступность** | 99,5% в рабочее время (с 07:00 до 21:00); ПЛР — не более 4 часов в месяц |
| **Производительность** | Открытие карточки пациента < 2 сек; формирование списка на месяц < 5 сек при нагрузке до 200 врачей одновременно |
| **Масштабирование** | На весь регион РТ (порядка 50 тыс. пациентов с гепатитами в регистре по оценке), с возможностью тиражирования в другие регионы |
| **Безопасность** | 152-ФЗ, приказ ФСТЭК №21, ПП-1119 УЗ-3, аттестация ГОСТ Р 57580 (по требованию) |
| **Размещение** | Целевая облачная платформа — только Yandex Cloud; конкретная конфигурация, регион хранения и соответствие требованиям безопасности должны быть согласованы с заказчиком до пилота |
| **Интегрируемость** | Стандартные медпрофили: HL7 FHIR R4, СЭМД/РЭМД, СМЭВ 3; нативное встраивание в интерфейс ГИС ЭЗ РТ |
| **Устойчивость к ошибкам** | Ручные корректировки врачом всегда выше автоматических правил; система объясняет свои рекомендации («назначено по КР: контроль УВО через 12 недель») |
| **Надёжность** | Никакое событие наблюдения не «теряется» бесшумно; все просрочки эскалируются по цепочке |

### 3.3.3 Основные сервисы backend (микросервисы или модульный монолит на первом этапе)

| Сервис | Ответственность |
|---|---|
| **API + Auth** | Единая точка входа, JWT/RBAC и аудит запросов |
| **Registry Service** | Ведение регистра пациентов, резольвция дубликатов, статусы наблюдения |
| **Clinical Rules Engine** | Модуль приложения для применения правил КР к данным пациента и расчёта планов/просрочек; версии правил фиксируются в коде и тестах |
| **Care Management Service** | Списки на приём, задачи для медперсонала, эскалация просрочек, журнал обзвона |
| **Notifications Service** | Шаблоны и тестовая очередь уведомлений, учёт согласий; реальные каналы в MVP не подключены |
| **Encounter Service** | Карточка приёма, текстовые заметки и черновики заключения |
| **YandexGPT Facade** | Единственная AI-интеграция: текстовый черновик по минимальному контексту; опциональная серверная интеграция, выключена по умолчанию и разрешена только для синтетических данных |
| **Integrations Hub** | Адаптеры к ГИС ЭЗ РТ, ЕГИСЗ, ФРВГ, ЛИС, СМЭВ; трансляция FHIR ↔ внутренняя модель; обработка входящих webhook/событий |
| **Analytics Service** | Встроенные сводные показатели на PostgreSQL; отдельное хранилище и BI-сервис не используем |
| **Admin & Audit Service** | Пользователи, роли, настройки МО, журнал действий, ИБ-события |
| **Scheduler** | Периодические задачи: ночной перерасчёт планов, рассылка напоминаний, расчёт просрочек, подъём эскалаций |

### 3.3.4 Поток данных (ключевой сценарий: постановка на учёт и первый визит)

```
1. ГИС ЭЗ РТ публикует событие «создан диагноз B18.2».
2. Integrations Hub получает событие и нормализует в FHIR Condition.
3. Registry Service создаёт/обновляет запись пациента в регистре.
4. Clinical Rules Engine по данным пациента рассчитывает стартовый план
   наблюдения по КР и кладёт задачи в Care Management.
5. Notifications Service создаёт тестовую запись приветственного уведомления
   с кратким маршрутом; реальная отправка включается только после подключения и проверки канала.
6. На рабочем месте врача пациент появляется в списке на ближайший месяц.
7. В день приёма врач открывает карточку, видит чек-лист обследований,
   вводит текстовые заметки; YandexGPT готовит черновик → врач проверяет и редактирует.
8. Заключение подписывается ЭП и возвращается в ГИС ЭЗ РТ через Integrations Hub.
9. Clinical Rules Engine по итогам приёма актуализирует план
   (например, назначает ПВТ → создаёт контрольные точки, включая УВО-12).
10. Встроенная аналитика приложения обновляет сводные показатели охвата
    и приверженности; отдельные BI-платформы не используются.
```

### 3.3.5 Технологический стек (выбранный)

> Облачный и AI-выбор намеренно ограничен двумя продуктами: Yandex Cloud — целевая платформа для приложения и БД; YandexGPT — единственная AI-интеграция. Остальные функции остаются в самом приложении.

| Слой | Технологии |
|---|---|
| Frontend врача | TypeScript + React; встраивание в интерфейс ГИС ЭЗ РТ (iframe/веб-компонент) |
| Backend | Python + FastAPI; модульный монолит без преждевременного выделения микросервисов |
| БД операционная | PostgreSQL (Managed Service for PostgreSQL в Yandex Cloud) |
| Аналитика | Встроенные сводные запросы к PostgreSQL; отдельная БД/BI-платформа не нужна |
| Очереди и фоновые задачи | Встроенный планировщик приложения; брокер событий не используем |
| Файловое хранилище | Не входит в объём текущего проекта |
| Аутентификация | JWT и RBAC внутри приложения |
| AI | YandexGPT для текстовых черновиков |
| Мониторинг | Средства Yandex Cloud и журнал приложения; отдельный стек мониторинга не добавляем |
| CI/CD | GitHub Actions для этого репозитория |
| Развёртывание | Docker для упаковки; целевая платформа размещения — Yandex Cloud, без отдельного Kubernetes-кластера в MVP |
